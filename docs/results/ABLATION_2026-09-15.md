# Ablation: dependency-aware stale-result rejection, 15 September 2026

The controller marks an accepted read as `stale` when a slot that the read depended on
changes. It then removes that result from planning evidence. This test measures what the
agent does when that step is disabled.

## Method

`Agent` accepts a `disabled` set. The name `dependency_invalidation` makes
`_invalidate_dependencies` a no-op. The controller then emits one
`ablation_skipped_invalidation` event that lists the changed slots and the affected calls.
The switch reaches the runner through `--disable dependency_invalidation`.

Two new live fixtures place a correction after a read returns, and no write is in flight at
that moment. This matters. `_cancel_writes` runs on every new input, but it cancels writes
only. If a write were pending, it would cancel the write first and hide the mechanism under
test.

| Fixture | The correction changes | Correct effect |
|---|---|---|
| `stale_read_after_correction` | the symptom | `order_replacement_part(Panel-A, PA-77)` |
| `stale_read_after_device_correction` | the device, not the symptom | `file_visit_request(Panel-B, Thursday, 10:00)` |

The second fixture is the harder one. The support notes differ per device. The obsolete row
stays superficially applicable, because the symptom did not change.

Models: `openai/gpt-oss-120b` and `openai/gpt-oss-20b` on Groq. The 20 B model is the weak
tier. It tests whether a smaller model is misled by obsolete evidence that a larger model
ignores.

The cohort is these cells and no others. `artifacts/ablation/` also holds local runs, pilots
and a later verification run, so the directory is not the cohort.

| Model | Fixture | Control | Ablated |
|---|---|---|---|
| `gpt-oss-120b` | symptom correction | 3 | 3 |
| `gpt-oss-120b` | device correction | 3 | 3 |
| `gpt-oss-20b` | device correction | 3 | 3 |

That is 18 runs. A fourth `gpt-oss-120b` device control exists and is excluded. It was run to
verify an unrelated controller fix, after the cohort was measured.
Runs are paced at 95 seconds, because one run needs about 9500 input tokens against an
8000 token-per-minute limit.

Scoring excludes `ablation_skipped_invalidation` from the unexpected-error check. The marker
is an error event, so it would fail the ablated arm by construction.

| Arm | Passed | Committed effect |
|---|---|---|

The ablation changed no task outcome in any of the eighteen runs. One ablated run of nine
emitted a spurious clarification. It asked for a day to book the service visit that the obsolete notes
recommended. No ablated run committed a wrong effect.

## What the mechanism does

The mechanism works, and a proposal-level probe shows it directly. Turn 4 of a local control
run holds two reads and one result:

```
ledger:   inspect_support_notes  stale     <- the obsolete read
          inspect_support_notes  success   <- the fresh read
evidence: [one result, the fresh one]
```

In the ablated arm the marker fires, the obsolete row stays in evidence, and the model reads
again anyway. The model does not need the controller to remove the row.

## What this means

1. State the claim carefully. This ablation shows that the mechanism is correct and
   observable. It does not show that wrong effects appear without it. A deck claim of
   "wrong or duplicate effects appear" is not supported by this evidence.
2. A strong model notices obsolete evidence without help. Both fixtures name the changed
   field inside the stale row, so the model can see that the row is for the wrong unit.
   Removing that field would hide it from the model, and that would test deception rather
   than staleness.
3. The value of the mechanism is a guarantee, not a repair. The controller drops obsolete
   evidence for every model. The alternative depends on model competence in every turn.
   State it as defence in depth.
4. The remaining untested case is a pending read, not an accepted one. Disabling
   invalidation lets an obsolete read run to completion. The result is then rejected by the
   dependency-currency check in `_result`, so the effect is wasted work and added latency,
   not a wrong answer. Measure that as a latency claim.

## Limits of this result

State only what the 18 runs support.

Supported: no committed-effect difference appeared between the arms in these runs.

Not supported, and not claimed here:

1. That a model never needs the mechanism. Two fixtures and two hosted models are a small
   sample. Both fixtures name the changed field inside the stale row, so a model can see that
   the row is obsolete without help from the controller.
2. That no local model can finish these fixtures. Two local models were tried on one card.
3. A universal bound on models above 4 B. The measured bound is this card, these two models
   and this fixture length.

This is also not an ablation of every stale-result defence. Only `_invalidate_dependencies`
is disabled. The currency check in `_result`, write cancellation on new evidence, argument
grounding and default-deny authorization stay active, and any of them can mask a difference.
It is an isolated test of one mechanism for reads that were already accepted.

The runs do not assert that the first read was accepted before the correction arrived. The
26-second gap schedules an event. It does not prove that the intended internal state was
reached. A later run must record that precondition instead of inferring it from the schedule.

## Stop condition

Defer further expansion of this ablation until multimodal integration and the Package 1
request-correctness work pass. Do not spend more quota waiting for a positive result.

A fixture that failed only because the stale row omitted the changed field would have to come
from a real interface contract and be specified before testing. Many real interfaces rely on
request provenance instead of echoing their arguments, so such a case is not automatically
deception. Inventing one to force a win would not be evidence.

## Local model

`qwen3:4b` completes neither fixture. The cause is not the ablation.

The probe shows the model proposes `inspect_support_notes` on every turn. It never sets
`write_requested`, so it never attempts a write. The controller ignores the duplicate call,
emits nothing, and the turn stalls until the scenario deadline.

The write-continuation constraint cannot correct this. The constraint gates on
`speech_write_requested`, which the controller sets from the model's own `write_requested`
flag. A model that does not recognise the write intent never sets the flag, so the
safeguard that forces a write to complete never starts. Record this as an open defect.

`qwen2.5:7b-instruct` is the other local candidate, and the card cannot run it at speed. Full
offload needs about 5100 MiB on a 4096 MiB card, so automatic fitting placed 12 of 29 layers
on the GPU. Each request took 51.6 seconds. The fixture completed three requests in 111.5
seconds, and the correction cancelled the first turn before the read returned, so the run
never reached the state under test.

| Model | Offload | Per request | Result |
|---|---|---|---|
| `qwen3:4b` | 37/37, pinned | 12 s to 14 s | Fast enough. Repeats the read and never writes. |
| `qwen2.5:7b-instruct` | 12/29, automatic | 51.6 s | Too slow. Three requests inside the cap. |

Record this as a hardware limit. A GTX 1650 with 4096 MiB cannot complete a three-turn local
scenario inside the 120-second cap with any model larger than 4 B. Use a hosted model for a
weak-planner arm, because hosted latency is not a constraint.

Local runs also need `ACCESSFLOW_OLLAMA_NUM_GPU=37` for `qwen3:4b`. Do not pin it for other
models. See the 15 September correction in `INFERENCE_TUNING_2026-09-14.md`.

## Pacing change

One uniform `event_spacing_s` cannot place a correction after a tool result on a slow
backend. The maximum is 5 seconds, and a local plan takes 12 to 14 seconds. `Scenario` now
accepts `event_gaps_s`, which supplies one gap for each pair of events. The replay budget
check is unchanged and counts the sum of the gaps.
