## What is committed

- `src/accessflow/adapters/vision.py` (new): `OllamaVisionProvider`, a plain
  `Callable[[Path], str]` matching `LocalPerception`'s injected `vision_provider` seam
  (`src/accessflow/perception/local.py`, unmodified). Reads a PNG, base64-encodes it, and
  POSTs one `/api/chat` request to a local Ollama server with the image attached. Bound by an
  explicit `timeout` (default 30 s, overridable). No automatic fallback: an HTTP error, a
  non-2xx status, or an empty model response raises and propagates; the caller never
  substitutes a scripted caption for a failed call.
- `src/accessflow/adapters/process_perception.py`: **not modified.** Its constructor already
  accepts `worker_args: Sequence[str]`, which is appended verbatim before `--model-path` when
  spawning the worker (see `_spawn_process`). The CLI supplies
  `["--vision-provider", "ollama", ...]` through that existing seam, so no new parameter or
  restructuring was needed there. Flagged explicitly because the task description named this
  file as an expected edit site; it was reviewed and found not to require a change.
- `src/accessflow/cli.py`: added `--vision-provider`, `--vision-model`, `--vision-url` to the
  `replay`/`suite` component parsers (mirrors the existing `--asr-model-path` pattern), a
  validation error when `--vision-provider` is set without `--components local`, and
  `component_config["vision_provider_requested"]` records the requested
  `"<provider>/<model>"` string, for example `"ollama/gemma3:4b"`. The key says "requested"
  because the committed worker rejects the options, so the parent cannot show that any
  vision backend ran. The observation backend field is the evidence of what served a frame.
  `"none"` is recorded verbatim when vision is not requested.
- `src/accessflow/evaluation/scenarios.py`: renamed `_resolve_audio_paths` to
  `_resolve_media_paths` and widened its `kind` check from `"audio"` only to
  `{"audio", "frame"}`. This file is not on the explicit "do not touch" list. The task
  description asserted that `load_scenario` already resolves a frame event's relative `path`
  against the scenario file's directory "the same way audio does"; on inspection that was not
  yet true (only `AudioEvent.payload.path` was resolved). Since resolving a committed PNG
  fixture's path independent of process cwd is required for this scenario to run correctly
  from any working directory, and the fix is a one-line, purely additive generalization of an
  existing private helper (same logic, same call site, no behavior change for existing audio
  scenarios), it was made here rather than worked around. No test referenced the old private
  name. Full test suite and ruff pass unchanged.
- `tests/fixtures/images/device_panel.png` (new fixture, see Fixture provenance below).
- `scenarios/live_dev/frame_device_panel.json` (new scenario, see below).

## Scenario: `scenarios/live_dev/frame_device_panel.json` (id `live-dev-frame-device-panel-01`)

One `frame` event (the PNG fixture above) and one `transcript` event. The transcript
("Book a Wednesday five PM service visit for the device shown in this photo.") deliberately
never names the device or its error code, and the one tool, `file_visit_request`, requires
`device` as a schema-required argument alongside `day`/`hour`. The only way to supply
`device` is for the model to read it off the image. `offline-fake` has no scripted
`proposals`/`reasoning_steps` for this file on purpose, matching `audio_correction.json`'s
convention: it fails loudly (`ValueError: Offline fake mode requires explicit proposals or
reasoning_steps`) instead of silently substituting a caption for vision. Verified:

```
.venv\Scripts\python.exe -m accessflow.cli replay scenarios\live_dev\frame_device_panel.json --backend offline-fake --output artifacts\check.jsonl
```

### Event order matters: frame before transcript, not after

The first attempt sent transcript before frame (mirroring `audio_correction.json`'s single-event
shape naively extended). That run reached `completion_status: "timeout"` after two
`no_dispatchable_call` errors and a `no_progress_exhausted` error, with **no** tool ever
proposed successfully, even though the vision observation did arrive with the correct
"PANEL-B" / "ERR-42" text.

Root cause, read from `src/accessflow/engine.py` (not modified): `_apply` only updates
`self.speech_write_requested` when the triggering observation's source is speech
(`if speech_origin:`, `_apply` around line 456). An image-triggered planning round can supply
information and prose, but per the code's own comment ("An image can invite an informational
answer on its own. It does not finish pending speech or authorize a state-changing action.")
it can never authorize a write. In the transcript-first ordering, the *last* round with a
complete, write-requesting proposal was the image-triggered round (transcript had already
asked its clarifying question and set `speech_write_requested=False` because it had to
clarify), so the write stayed permanently blocked (`blocked_calls` incremented silently in the
write-gating branch, no per-call diagnostic emitted) until the bounded retry budget was
exhausted.

The scenario now delivers the frame first, with a 55-second explicit gap
(`"event_gaps_s": [0.01, 55]`, `"completion_timeout_s": 30`, total budget 85.01 s, under the
114 s internal ceiling) before the transcript. This is not a workaround for a bug; it mirrors
a realistic usage order (show the device, then state the request) and is required by the
engine's own write-authorization design so that the transcript-triggered round is the one
that both has the device slot available (from the already-completed image observation) *and*
is eligible to set `speech_write_requested=True`. This finding, and the 55 s figure, are
reported as this session's own diagnostic work, not a claim about engine.py's correctness.

`expected_slots`/`expectation` only pin `day: "Wednesday"` (deterministic from the scripted
transcript) plus `final_basis: "confirmed_tool_effect"` (a write must actually commit). The
`device` value is real, live, vision-model output and is reported below, not hard-pinned in
the oracle, the same conservative choice `audio_correction.json` makes for `hour`.

```
  --vision-provider ollama --vision-url http://127.0.0.1:11435 `
  --backend groq --request-timeout 30 --inference-timeout 60 `
  --output artifacts\frame_vision_e2e.jsonl
```

`--asr-model-path` is still required even though this scenario has no `audio` event: the
persistent worker process (`ProcessPerception`) refuses to start without an installed model
path (`src/accessflow/adapters/process_perception.py::_ensure_process`), and that file was
deliberately left unmodified (see above). Model directory is the same
`Systran/faster-whisper-base.en` snapshot already measured in
`docs/results/ASR_LOCAL_2026-09-15.md`.

`--inference-timeout 60` overrides the Agent default of 25 s. A standalone measurement of
`OllamaVisionProvider` against this fixture (before wiring the scenario) took 45.4 s on a
cold model and ~20.5 s once warm; the default 25 s deadline (which bounds both the perception
call and each planning call, see `engine.py::_bounded`) would truncate a cold vision call.
This was measured, not guessed, before choosing the override.

Local Ollama vision server: `http://127.0.0.1:11435`, model `gemma3:4b` (`capabilities:
["completion", "vision"]`, confirmed via `POST /api/show`). One hosted Groq call had already
run against this scenario during debugging (the transcript-first attempt above); this run
followed it by several minutes of file editing and test work, well clear of the 70-second
pacing floor in `docs/PROFILES.md`.

## Limits

- One fixture, one scenario, one live run reported in full above (plus the transcript-first
  attempt that correctly failed and is reported for what it showed, not discarded).
- The `device`/`error_code` slot text is real model output on a specific run; a different
  model or prompt could phrase it differently (e.g. casing), which is exactly why the oracle
  does not pin it.
- Vision latency is measured on one local CPU/GPU configuration and is not a benchmark claim.
- No held-out, clinical, or photographed-device evidence is claimed. The fixture is
  synthetic and its provenance is above.
